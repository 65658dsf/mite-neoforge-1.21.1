# 验收矩阵与逐功能交付门槛

开发署名：NingMeng123。原作：Avernite。初始状态：下表均为**待实现 / 待验收**，不是测试结果。

## 每个小功能的固定流程

根据用户新增要求，每个小功能按下面顺序独立完成：

1. 记录规则来源、预期行为、现代适配差异和具体实机步骤；实现相应代码与资源。
2. 通过编译和该功能必要的规则测试、GameTest、数据验证；失败先修复，不能将预期失败记录成通过。
3. **实际启动并打开 Minecraft 客户端进行游戏测试**。涉及联机的功能同时启动独立服务器并由客户端连接；只出现主菜单不等于相关玩法通过。
4. 记录测试世界、mod 构建、操作、结果、日志和需要时的截图。客户端 UI、容器和动作必须观察实际显示/交互；无头 GameTest、编译、日志启动成功均不能替代此步骤。
5. 游戏内确认成功后，用中文描述创建该功能 commit，再 push 到已经确认的 GitHub 项目仓库。开发者署名使用 NingMeng123；`https://github.com/65658dsf` 是账号地址，不能据此编造具体仓库远程地址。

无法打开游戏、无法完成场景、缺少服务器、Git 远程未确认或 push 失败时，明确记录阻塞项，不标记“已交付”。不得为了 push 把未成功测试的功能写成已验证。文档和纯提取工具可作为准备工作记录，不声称它们通过了游戏内玩法测试。

每条功能记录至少包含：功能 ID、R196 来源或 `modern_design`、预期行为、构建版本、自动测试结果、实机步骤与结果、客户端日志位置、专服结果（适用时）、中文 commit SHA、push 分支/结果。状态依次为 `planned → implemented → automated_passed → in_game_passed → committed → pushed`，不可跳级。只在全部条件满足后标为交付完成。

## 验收证据要求

数值测试预期从独立原始规格或明确现代设计表读取，避免只是复述当前实现。概率规则固定随机种子检查边界和样本分布；不以一次偶然掉落判定概率正确。输入/输出资源守恒要计算容器余物、经验和耐久，不只比较产物数量。

每个有界临界值至少验证低于、等于、高于阈值；每个网络交互验证单人、专服、两个玩家和重连；每个持久状态验证重启和跨维度。性能报告记录机器配置、Java 参数、世界 seed、视距、实体/机械数量、基准版本及采样时间；指标缺少参照时报告观察结果，不能宣称已达到未定义的性能目标。

完整复刻发布条件：所有适用条目均为 `pushed` 且有游戏内验收记录，所有 R196 证据缺口已关闭或经用户明确接受为偏离，现代注册项清单无未分类项。存在任意上述缺口时版本必须标为开发预览并列出未完成项。
