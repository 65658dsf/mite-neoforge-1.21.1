## 上限入口与默认行为

`yc.java:468`（`Item.java`）的初始 `cw` 是 **16**。物品构造器会调用 `d(int)` 覆盖它；耐久物品构造阶段设置为 1。方块注册的最终阶段 `aqz.java:2538-2542` 会再次把每个方块的 `getItemStackLimit()` 写回对应 ItemBlock，因此提取顺序必须完成方块注册后再读取。

直接查询确认 221 个方块中所有具有对应注册物品的条目，其方块 `max_stack_size` 与物品默认上限一致。内部世界方块仍保留来源分类，是否映射成玩家可获取物品由现代适配处理。

`ye.java:180-185`（`ItemStack.java`）区分两个问题：

- `e()` 返回物品对当前 subtype、damage 的堆叠上限。
- `f()` 判断是否可堆叠：`上限 > 1 &&（物品没有耐久，或当前 damage == 0）`。

损伤没有独立改变 getter 的数值；它影响可堆叠判断。全部默认注册的可损坏物品上限都是 1，因而没有“未损坏工具能多件叠放、使用后突然变成单件”这种默认规则。

## 唯一动态上限：雪层

全反编译代码检索及所有注册物品实际反射结果一致：667 个物品中，666 个继承 `yc.getItemStackLimit`，只有 `zc`（`ItemSnow.java`，源物品 ID 78）重写该入口：

```java
return subtype == 0 ? super.getItemStackLimit(subtype, damage) : 8;
```

来源默认值是 **32**，所以单层雪 subtype 0 的上限为 32，其他深度 subtype 1 至 7 的上限均为 8。该完整范围已单独直接查询。

R196 雪的创造物品枚举只提供 subtype **0、3**；`getNumSubtypes() == 2` 是枚举数量，不能据此猜测有效 subtype 为 0、1。旧 subtype 3 对应四层雪，其名称后缀为 `.slab`。新版雪物品只有一层雪的常规物品形态；多层携带形式如何保存和恢复，需要现代实现明确处理。

## 合并身份：不能只比较物品 ID

`ye.java:388-460` 的严格物品栈比较包含：

1. 相同物品 ID。
2. 相同 subtype。
3. 相同伤害值（调用方明确要求忽略伤害时除外）。
4. 相同品质（调用方明确要求忽略品质时除外）。
5. 相同 `is_artifact` 标志。
6. 相同数量（调用方明确要求忽略数量时除外）。
7. 同样的 NBT/tag compound（调用方明确要求忽略 NBT 时除外）。

附魔、自定义名称、书内容等作为 tag compound 的一部分影响合并。附魔不是另一套统一的堆叠上限，也没有“有 NBT 就一律不能堆叠”这种规则；相同内容的物品仍按其物品上限处理。

提取器直接执行八个相等判断：忽略或保留数量、不同 NBT、明确忽略 NBT、不同 artifact、不同 subtype、不同伤害、明确忽略伤害，结果均符合上述调用参数。

`ye.java:1141-1167` 的唯一签名用于全世界唯一物品的追踪，不提供额外的堆叠上限入口。唱片和成书在自身构造器中已经设为单件；不能根据签名字段的存在再发明另一条普通物品的堆叠公式。

## 背包、容器和自动化

此部分以来源调用链核对，不声称提取器实际启动了这些容器。

- `ud.java:185-191` 的背包寻找合并槽要求当前栈可堆叠、尚未到物品上限及库存上限，并使用忽略数量的严格身份比较；`ud.java:563-564` 的库存基础限额为 64。
- `ud.java:288-334` 的加入现有栈最多补至物品上限或库存上限，取两者中较小的值。`ud.java:376-387` 的 `addItemStackToInventoryOrDropIt` 对超限输入先分栈，再存放或丢弃。
- `uy.java:224-250` 的普通点击合并同时限制槽位容量与物品容量。`uy.java:386-434` 的 Shift 转移使用可堆叠判断及身份比较；旧代码在这一调用中明确允许忽略伤害，但所有默认可损坏物品已经是单件，不能据此放宽新版装备组件。
- `we.java:112-114` 的槽位上限委托库存；专用槽的可放入、锁定或容量规则仍要保留，不能统一强制设为 64。
- `asi.java:267-291, 326-331`（漏斗）使用忽略数量的严格身份比较，合并量最多为物品上限减去目标数量；自动化同样不能绕过物品限额。

旧构造器和某些空槽直接赋值分支本身并不钳制全部输入数量。命令或损坏存档制造的超限栈不能被当成正常容量；现代实现需要在兼容旧数据时显式、安全地分栈，不能直接截断导致丢物品。

## 地上物品合并与新版差异

`ss.java:138-169`（`EntityItem.java`）要求相同物品实例、相同 NBT 存在情况及相同 NBT 数据、拥有 subtype 的物品 subtype 相同。它先选择数量较大的实体作为目标；只有 **两堆总和不超过上限** 才把整个小栈合入目标，否则整个合并不发生。没有先填满目标、再保留剩余的部分合并。

例如石头上限为 4，地上两堆数量为 3、3：R196 保持 3、3；不能变成 4、2 后仍称地上合并完全一致。3、1 可以合成 4。下个 tick 重试也不会使 3、3 逐渐合并。已检查的 Minecraft 1.21.1 `ItemEntity.areMergable` 也先校验总量不超过上限；本批保留这个现有条件，真实 GameTest 覆盖 3+3 不合并、2+2 合并，无额外地上合并 Mixin。

旧地上合并不单独比较品质、artifact、damage，但每个默认可损坏物品上限都是 1，两个正常单件装备无法合并。现代版使用 Data Components 表达品质、名称、附魔、来源标签；保留组件相等校验可以保护额外现代状态，不能删掉所有组件比较来机械模仿旧代码的遗漏。
