# R196 玩家规则静态规格

分析与开发署名：NingMeng123。依据：本地 `MITE 1.6.4 R196.zip`、CFR 0.152 生成的 `.reference/r196/decompiled/`。这是规则证据，不表示对应现代功能已经实现或完成游戏验收。结构化数据见 `spec/r196-player-rules.json`。

下文行号为当前反编译文件行号。`uf`=EntityPlayer，`ux`=FoodStats，`jv`=EntityPlayerMP，`of`=EntityLivingBase，`hn`=ServerConfigurationManager，`aaw`=EnchantmentHelper，`yc`=Item。所有整数除法按 Java 向零截断；每 tick 的累积使用 Java `float`，不能将理想平均周期当成精确触发 tick。

## 经验表字节码修正记录（2026-10-12）

原发布包 `uf.class` 与本地提取文件逐字节相同，SHA-256 为 `6aadb6b6596d5328fe512a14f1714abb44b9d1dcc791d0b3abb2349140aeca19`。`javap -c -p uf` 的 `<clinit>` 偏移 18–20 将步长设为 20；31–34 先把当前步长加入累计值；35 才将步长加 10；38–43 保存累计值。CFR 0.152 将其错误折叠成先增加步长的表达式，导致早期文档中的一级 30 XP 和 `5L²+25L` 错误。本次按字节码纠正，连同依赖一级阈值的死亡惩罚说明一起修正；生命与食物容量公式不受影响。

正确累计阈值：一级 20、二级 50、五级 200、十级 650、三十五级 6650、两百级 203000。该证据修正不代表死亡惩罚已实现。

## 饱食、营养与基础代谢

- 饱食 `satiation` 与营养 `nutrition` 是两个独立整数；两者上限都与生命上限公式相同。新建 FoodStats 时两者都设为当时的营养上限。`isHungry` 判断饱食等于 0，`isStarving` 判断营养等于 0；不能用现代原版一个食物条替代二者语义。证据：`ux.java:14-17,174-179`，`uf.java:1727-1740`。
- setter 在 `check_limit=true` 时仅做 `min(value,limit)`，没有隐含下限钳制；规格不能把它改写为双边 clamp。吃食物依次增加饱食、营养；服务端再增加胰岛素抵抗和微量营养素。证据：`ux.java:19-25,156-170`。
- 正常服务端更新每 tick 调用 FoodStats。幽灵、特定锦标赛身份、死亡/移除状态或生命不大于 0 会提前返回。创造模式不扣微量营养；创造或无敌能力阻止 `addHunger`。证据：`jv.java:471-558`，`ux.java:36-49,117-125`，`uc.java:18-24`。
- 基础饥饿累积 `0.002f * wetnessAndMalnourishmentMultiplier`；统一累积方法乘 `global_hunger_rate`（字段默认 `1.0f`），并以上限 `40.0f` 截断。非创造模式另将 `hunger_for_nutrition_only` 增加 `0.002f*0.25f`。证据：`ux.java:12,28-58,117-125`。
- 若普通饥饿累积达到 `4.0f`，本次更新仅减去一次 4：两项食物值至少一项大于 0 时，若饱食不足 1，或“营养专用累积 + 0.001f 达到 4 且营养仍大于 0”，扣 1 营养并清空营养专用累积；否则扣 1 饱食。这里是 `if`，不是清空积压的 `while`。证据：`ux.java:50-60`。
- 特定条件 `inBed() && isOnHitList()` 额外增加 `0.002f*20.0f` 饥饿，发生在本 tick 的食物扣减判断之后；不能描述成所有玩家睡眠都额外消耗 20 倍。证据：`ux.java:61-63`。
- 旧客户端额外饥饿累积超过 `0.2f` 时发送 `Packet82AddHunger` 并清零。现代实现应重新划分服务端计算与客户端表现，不能照搬客户端申报的信任边界。证据：`ux.java:117-142`。

## 回血、饥饿伤害与微量营养素

**营养为 0 时**：回血进度清零；饥饿伤害进度每 tick 加 `0.002f`。达到 1 后，只有 `health>10 || difficulty>=3 || (health>1 && difficulty>=2)` 时尝试造成 1 点饥饿伤害；无论是否造成伤害，进度减 1，营养专用饥饿累积清零。正常模式有 1 点生命阈值，困难模式允许致死；不要忽略原表达式在低难度且生命大于 10 时仍成立。证据：`ux.java:64-73`。

**营养非 0 时**：饥饿伤害进度清零，回血进度增量为：

```text
(0.0004f + nutrition * 0.00002f)
* (malnourished ? 0.25f : 1.0f)
* (inBed ? 4.0f : 1.0f)
* (1.0f + highestWornRegenerationEnchantmentLevel * 0.5f)
```

仅在 `naturalRegeneration=true` 且 `0<health<maxHealth` 时，进度达到 1 才治疗 1 点、额外增加 1.0 饥饿、进度减 1。否则回血进度清零。床上是 `inBed` 条件，并非仅熟睡状态；附魔等级取已穿装备中的最高等级，不是各件相加。证据：`ux.java:74-85`，`uf.java:1802-1803,1917-1920`，`aaw.java:120-133,333-334`。

蛋白质、必需脂肪、植物营养素的初值/上限均为 160000，setter 限制 `[0,160000]`。每个正常非创造更新 tick，仍大于 0 的每项减 1。食物对应类别为真时补充 `itemNutrition*8000`，否则为 0；小麦种子 `yc.U` 另补 2000 必需脂肪。证据：`jv.java:91-93,295-329,366-384`，`yc.java:44,1531-1540`。

**R196 的营养不良只看蛋白质或植物营养素是否为 0**；双重营养不良判断两者都为 0。必需脂肪虽被存储、消耗和补充，但不参与这两个判断，且不能把双重营养不良擅自叠加为两次饥饿/回血惩罚。证据：`jv.java:1257-1262,1524-1525`。

## 雨、水与胰岛素抵抗

湿冷代谢公式：

1. 暴露于雨中：雷暴取 `rain=0.5f`，普通雨取 `0.25f`，否则 0。
2. 脚部坐标 `y+1` 为水取 `immersion=0.5f`；否则脚部 `y` 为水取 `0.25f`；否则 0。
3. `wetness=max(rain,immersion)`。普通雨中且 `immersion==0.25f`，另加 `0.125f`。
4. 冻结群系将 wetness 乘 2；否则群系温度不小于 `desertRiver.F`（注册值 1.4f）时 wetness 清零。
5. 最终 `multiplier=1+wetness+(malnourished?0.5f:0)`，营养不良项不随寒冷翻倍。

证据：`jv.java:1508-1525`，`acq.java:34`。该方法的 CFR 输出在 1513 行有局部变量还原瑕疵，已用原始 `jv.class` 的 `javap -c -p` 交叉核对：字节码偏移 15–46 完整计算 rain 并写入局部槽 4，随后参与 `Math.max`，上述公式不依赖错误的临时变量文本。

胰岛素抵抗范围 `[0,192000]`，正常非创造更新每 tick 减 1；食物增加量是 `(int)(sugarContent*4.8f)`。进入轻/中/重度的数值阈值分别为 48000/96000/144000，但**状态回落有滞后**：数值归 0 才清除状态；低于第一个阈值但已有状态时保留轻度；数值对应的新等级低于旧状态时使用 `newLevel.getNext()`。不能每 tick 仅按三个阈值重新赋状态。证据：`jv.java:310-350`，`yc.java:1145-1146`，`EnumInsulinResistanceLevel.java:5-7,81-90`。

中度/重度不能代谢糖分。含糖食物的饱食值在糖量小于 1000 时减 1，否则减 `sugarContent/1000`；正向增加抵抗且已有抵抗状态时添加 400 tick 恶心，放大等级为状态 ordinal；重度另添加 `max((int)(addedResistance/48.0f),100)` tick 中毒，等级 0。证据：`uf.java:2640-2641`，`yc.java:1127-1134`，`jv.java:387-393`，`ni.java:22,32`。

## 死亡、重生和持久化

- 死亡时总经验不足 20 才设置 `respawn_experience=max(XP-20,-800)`；否则保持该字段原值，它的初始值为 0。不能简化为“每次死亡只减 20 XP”。证据：`jv.java:47,753-778`。
- 重生管理器先创建新玩家，再赋 `respawn_experience`，并复制三种微量营养素、胰岛素抵抗数值和状态、技能等，随后调用玩家复制方法。正常死亡的 `keepInventory` 分支会将原总经验覆盖回来；非死亡/保留分支还复制原生命及 FoodStats 对象。证据：`hn.java:221-250`，`uf.java:1852-1864`。
- 因而死亡不会自动清除微量营养不良或胰岛素抵抗。普通新 FoodStats 使用其构造时上限；不要未经调用顺序分析就把重生食物值补到最终等级上限。
- 死亡设置重生倒计时 120；倒计时方法在世界时间整 20 tick 时减 1。`afterRespawn` 设置保护计数 60；保护期伤害代码另有坠落/特殊伤害来源例外。这里只确认计数与判断，自动重生触发和登录中断流程尚未完整审计。证据：`jv.java:406-409,778,784-809`。
- FoodStats 存档保存 `fullness`、`nutrition`、`heal_progress`、`starve_progress`、`hunger`、`hunger_for_nutrition_only`。玩家经验读取 `experience`，若存在旧 `XpTotal` 则后者覆盖；微量营养和抵抗另行持久化。证据：`ux.java:89-106`，`uf.java:865-870`，`jv.java:123,148-152,195-204`。

### 死亡与负等级字节码复核（2026-10-12）

- `jv.<init>` 偏移 87–89 把待重生经验初始化为 0；`jv.a(nb)` 偏移 133–175 明确比较 `<20`、减 20、钳制 −800。高经验分支跳过赋值，每次正常重生新建玩家，因此通常归零。
- `jv.a(by)`、`jv.b(by)` 偏移 5–13 分别读写 `respawn_experience`。正常退出先保存玩家，重登恢复死亡生命状态与待重生值；只有真正请求重生才调用 `hn.a(jv,int,boolean)`。这不代表崩溃或保存失败后的回滚已验证。
- `hn.a(jv,int,boolean)` 偏移 171–177 把旧待重生值赋给新玩家，319 调用复制。`uf.a(uf,boolean)` 偏移 15–20 / 85–90 分别由 keepAll / keepInventory 覆盖回原经验。
- `uf.getExperienceValue()` 偏移 18–24 是 `totalXP / 3`；keepInventory 返回 0，负经验不会进入分球循环。`of.aB()` 在死亡动画第 20 tick、逻辑服务端、doMobLoot 开启时分球。球带原玩家名字，仅该玩家可拾取；初始 Age 为 −18000，到 6000 消失，共 24000 加载 tick。235 点死亡掉 78 点，按 73、3、1、1 分球；球数量与经验点数不能混淆。
- `avj`（GuiIngame）只显示非零等级，负数颜色为 `0xFF1313`，正数为 `0x80FF20`，四向黑描边。条宽仍为 `int(progress*183)`，负级经验条保持绿色。骑马跳跃条优先，书本界面隐藏显示。
- 创造模式的负经验等级查询返回 0，但不会删除原始负经验；原发布包 `in_dev_mode=false`，正常模式入口锁定生存。旧版不存在旁观模式。

### 死亡经验球补充核对

`oa.l_()` 偏移 149–216 的归属分支同时限制吸引目标，不只是拾取权限；找不到归属玩家时不会主动选陌生人。旧代码没有主动清除失效缓存目标，现代适配应清理死亡、离线或跨维度的对象引用。`oa.b_(uf)` 偏移 10–54 先检查可达性、冷却，再检查所属名字；射线是从球中心向玩家身体 25%/50%/75% 高度检测，任一通过即可，窄物理规则可忽略铁栏杆等，不等同普通视线。

20 tick 延迟依赖尸体 `DeathTime==20`，到点时才读取位置、经验量和规则。静态调用链显示提前重生会移除旧尸体且没有独立补发；普通断线保存 DeathTime，重登后继续更新。为适配新版立即重生，现代端采用独立可保存的延迟队列，差异见 [死亡经验球适配](death-orb-adaptation.md)。

## 1.21.1 最小生命上限功能的接入证据

已检查 `build/moddev/artifacts/neoforge-21.1.259-sources.jar`，以下是建议，未在此分析任务中编写功能代码。

- `Attributes.MAX_HEALTH` 是可同步属性（`net/minecraft/world/entity/ai/attributes/Attributes.java:66-67`）。最小实现可在逻辑服务端设置其基础值，再仅在当前生命超过新上限时向下限制；升级不补血。不需要为第一项生命规则新增自定义网络包或 Mixin。
- 使用 `PlayerEvent.PlayerLoggedInEvent`、`PlayerEvent.PlayerRespawnEvent` 做生命周期更新，服务端 `PlayerTickEvent.Post` 做幂等校验，以覆盖命令直接设等级、经验变化和重生后的属性状态。事件类证据：`PlayerEvent.java:422-449`、`PlayerTickEvent.java:45-55`；后者在客户端也触发，必须限制为 `ServerPlayer`。
- 不宜只依赖 `PlayerXpEvent.LevelChange`：`Player.java:1709-1718` 在实际修改等级之前触发该事件，且可取消/改值；`ServerPlayer.java:446-448` 的 `setExperienceLevels` 直接赋值并绕过此事件。
- 原版属性自动同步适用于单人内置服务器和独立服务器；公共规则层不得引用 `net.minecraft.client`。跨维度及末地返回可通过 Post 幂等校验或 `PlayerChangedDimensionEvent` 补充覆盖。
- 若第一步暂时以现代 `experienceLevel` 驱动生命曲线，应在实现状态明确这只是生命曲线的独立交付；它不会自动实现 R196 自定义总经验曲线、负等级和死亡扣级规则。

验收向量：等级 0/4→6，5/9→8，10→10，30/34→18，35/200→20；降级限制当前生命，升级保持原生命；重新登录、死亡重生、`keepInventory`、命令直接设置等级、跨维度、单人和独立服务器均需实测。创造/旁观策略及与其他模组的额外生命修饰符行为需在具体功能中明确；R196 的上限公式本身没有创造模式特判。
