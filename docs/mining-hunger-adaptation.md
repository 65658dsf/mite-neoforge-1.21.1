# 食物能量不足时的采集减速

开发者：NingMeng123。依据为本地 MITE R196 发布包的原始字节码；本文记录规则与本轮适配选择，不表示已经完成游戏验收。

## 原始证据

`uf.hasFoodEnergy()` 判断的是 `satiation + nutrition != 0`（`uf.java:1735–1736`）。字节码偏移 1、5 分别读取两项，8 执行整数相加，9–17 根据和是否为零返回布尔值。正常非负数据中，必须两项都为零才没有能量；饱食为零但营养仍有 1 点时不会触发这项采集惩罚。

`uf.getCurrentPlayerStrVsBlock` 先处理水下惩罚（偏移 328–351），再处理浮空惩罚（353–366），随后在没有食物能量时把强度除以 `5.0f`（368–381），最后乘等级倍率并应用便携下限（383–404）。对应反编译位置为 `uf.java:819–828`，没有职业技能开关或按剩余食物比例计算的分支。

运算顺序必须保留：`strength = strength / 5.0f`，然后才执行 `strength *= 1.0f + level*0.02f`。例如输入强度 1、5 级、无能量时，结果 bits 应为 `0x3e6147af`；先乘等级再除以 5 会变成 `0x3e6147ae`。

## 现代适配

当前模组仍使用现代 `FoodData`，尚未实现 R196 独立的饱食和营养资源。本轮暂用 **`foodLevel > 0` 表示有能量**：食物条清空时强度除以 5，恢复到 1 点即恢复正常，没有按容量百分比、半条或其他比例设置门槛。现代 `saturationLevel` 不被解释为旧版 `nutrition`，也不单独决定本轮能量状态。

在现代工具与环境修正产生的强度上，先应用一次食物惩罚，再应用已有等级倍率；不重复计算水下、浮空、药水或工具效率。创造与旁观保留现代行为。已取消事件及非正强度仍由现有接入层阻止破坏进度，不因饥饿逻辑重新获得破坏能力。

本轮沿用 [基础挖掘进度](mining-base-adaptation.md) 与 [等级倍率](mining-level-adaptation.md)。零硬度的正强度仍能瞬破；取消或非正强度的现代保护仍优先于纯公式。食物恢复、死亡重生和重登之后，应使用当前同步的食物值重新判断，不缓存一个可能过期的饥饿标志。

## 独立验收向量

下表输入强度均为 1，食物条为空，目标硬度为 0.5；所有运算与累计均按 Java `float`。这里是预期数据，不是游戏实测结果。

| 等级 | 修正后强度 bits | 单次进度 bits | 客户端有效累加次数 |
| --- | --- | --- | --- |
| 0 | `0x3e4ccccd` | `0x3a4ccccd` | 1281 |
| −40 | `0x3d23d70d` | `0x3923d70d` | 6401 |
| 5 | `0x3e6147af` | `0x3a6147b0` | 1164 |
| 35 | `0x3eae147b` | `0x3aae147b` | 753 |
| 200 | `0x3f800000` | `0x3b800000` | 256 |

0 级食物为 1 或更高时，强度为 1，泥土仍为 256 次；空条时为 1281 次，不能将浮点逐次累加直接替换为 `256×5=1280`。1281 次在 20 TPS 下对应约 64.05 秒有效采集时间，不包含开始输入、连挖冷却和通信。现代服务端的经过 tick 数计算及 STOP 容差继续保留，因此不要求其累计过程与客户端位级相同。

另需验证取消、非正速度、创造/旁观、食物 0→1 与 1→0、等级倍率只应用一次，以及客户端与服务端的当前食物值一致。

## 保留的差异

R196 便携方块在全部修正之后取 `max(强度,4*硬度)`，可能抵消饥饿惩罚（`uf.java:787–788,828`）。例如工作台恒可便携（`arv.java:102–103`）。该下限仍未移植，现代工作台和容器继续受本轮食物惩罚；不能把这一差异写成原作一致行为。

空手、错误工具与材料门槛另行实现。当前没有燧石开局工具及配方闭环，本轮不增加原木封锁，也不把食物减速视为完整 R196 生存、营养或采集复刻。
