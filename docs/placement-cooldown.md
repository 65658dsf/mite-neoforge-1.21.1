# 放置后冷却与 R196 证据

由 NingMeng123 维护，更新于 2026-11-07。

## 当前行为

首次放置立即执行。普通方块在客户端预测成功后启动 **250 毫秒** 冷却，成功倒出桶的客户端预测启动 **500 毫秒** 冷却，现代粉雪桶也按 500 毫秒处理。两类操作共用客户端玩家的截止时间，按现实经过时间计时。后续点击在截止时间到达后执行，冷却中的点击直接拒绝，保持原有截止时间。

- 点按与长按共用同一锁。被拒绝的点击即时结束，长按由后续输入检查再次尝试。
- 热栏换槽、切换主副手、切换方块或桶类型均继续使用同一截止时间。
- 客户端在放置冷却期间拦截整次右键入口，包括开箱、工作台和进食。冷却结束后，这些交互恢复正常处理。
- 客户端生存与创造模式均执行成功放置后的输入冷却。服务端对两种模式的有效操作即时处理，继续执行权限、饥饿、碰撞和 NeoForge 放置事务等对应校验。
- 客户端碰撞失败、无效目标等失败尝试即时结束。服务端在收到请求后处理真实放置，取消事务会回滚放置。
- 睡莲等从对空气使用入口进入放置的方块也经过实际 `BlockItem.place` 判定。粉雪桶通过方块放置路径记录桶的冷却时长。
- 生存玩家饥饿值为 0 时拒绝放置方块和倒出桶，即使另一路营养值尚有剩余。恢复至少 1 点饥饿值后可再次放置。此判定只用于放置，其他右键交互继续受上述客户端输入锁管理。
- 死亡克隆、离线和换维度清理旧状态。仅客户端玩家保存冷却截止时间，按玩家对象实例隔离，使用线程安全的弱身份键表。

桶的客户端预测成功后记录输入冷却。服务端的饥饿等拒绝判定发生在消费桶、支付源水经验、释放桶内生物之前。被拒请求对应的 Ctrl 输入意图随本次请求消费，后续倒水使用各自的输入意图。

客户端使用原版即时预测。若本地预测成功、之后被服务端事件取消，本地可能继续执行本次剩余的 250 或 500 毫秒输入冷却。时间锁由客户端管理，服务端处理每次收到的有效请求。这样可以适应网络抖动造成的收包间隔变化，例如客户端相隔 250 毫秒发出的两次合法操作在服务端可能相隔 249 毫秒处理。

普通水桶与鱼、蝌蚪、美西螈桶使用临时水，Ctrl 加 100 经验点可换永久源水。临时水 16 tick、岩浆 48 tick 的流体消退计时独立于本节的玩家输入冷却。

此前项目曾按用户要求采用 6、8、10 tick 的统一放置时长。下方历史验证章节保留当时数值，当前规则以上述毫秒时长为准。

## 复测

1. 静止单击放一块，应立即出现。立即换槽或换手尝试另一块应被拒绝，到期后再次点击应立即放下。被拒绝的点击应在当次结束。
2. 普通方块长按连续放置时，相邻客户端成功预测间隔至少 250 毫秒。倒桶后等待至少 500 毫秒再执行下一次放置。快速连点、松键再按、跳跃及换槽均应沿用原截止时间。单人内置服与独立服务器分别复测，服务端应接受因网络抖动而缩短处理间隔的有效操作。
3. 检查计时依据现实经过时间。正常 20 TPS 下 250 毫秒约为 5 tick，500 毫秒约为 10 tick，客户端输入检查时机可能使实测间隔更长。
4. 放置后立即尝试开工作台、开箱或进食，应在本次输入锁到期后才可执行。没有活跃放置锁时，这些操作直接进入各自交互流程。
5. 分别测试碰撞失败和服务端事件取消。只有客户端预测成功时可能留下本次本地输入锁，服务端应回滚取消的放置，并立即按正常校验处理后续合法请求。
6. 普通桶、Ctrl 桶、六种生物桶和粉雪桶分别核对即时倒出、500 毫秒冷却、源水经验与单次释放。被拒请求应在消费满桶、扣费和释放生物之前结束，并消费本次 Ctrl 输入意图。
7. 吃蓝莓和放睡莲，检查进食与放置分别使用对应流程。生存饥饿值为 0 时拒绝放置，恢复饥饿后可重试。创造客户端成功放置后也应执行 250 或 500 毫秒输入锁，服务端对创造与生存的有效操作均即时处理。

实际客户端操作手感、网络抖动和真实多人行为需通过客户端验收，自动服务端测试与客户端变换审计分别覆盖各自代码路径。

## 2026-10-26 单人冷却失效修复

原来的 `WeakHashMap<Player, Cooldown>` 使用 `Entity.equals/hashCode`，仅按实体 ID 区分玩家。单人客户端与内置服中的玩家 ID 相同、世界对象不同；一端查询另一端写入的冷却时，世界检查会删除该记录，使预测与服务端的冷却互相清除。改用 `MapMaker.weakKeys()` 的实例身份比较，保留弱引用回收与并发访问支持。

- 新增三个集成回归：同 ID 的另一世界玩家查询、写入及清理不影响原截止时间；同一玩家修改实体 ID 后仍处于冷却。
