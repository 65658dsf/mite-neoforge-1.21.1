# 放置后冷却与 R196 证据

维护者：NingMeng123。更新日期：2026-10-26。

## 当前行为

首次放置立即执行，不等待、不暂存动作。生存玩家实际成功放置方块或倒出桶后，共享 **8 tick（正常20 TPS下0.4秒）** 的冷却；到期后的新请求立即执行。冷却中的请求直接拒绝，不延长截止时间，也不会在到期后自动补放。2026-10-24 按用户要求由6tick略微增加，历史验证记录中的旧时长保留。

- 热栏换槽、切换主副手、切换方块或桶类型不能绕过同一玩家的冷却。
- 服务端放置失败或被 NeoForge 事件取消不启动冷却；拿着方块开工作台、开箱以及蓝莓种植失败后转为进食，仍按各自原生交互处理。
- 睡莲等从对空气使用入口进入放置的方块也经过实际 `BlockItem.place` 判定，粉雪桶走同一方块放置路径。
- 创造模式保留即时放置的既有豁免；死亡克隆、离线和换维度清理旧状态。
- 已删除待执行放置队列与玩家 tick 重放。客户端同步成功后八 tick 的重复使用节奏，避免原生四 tick 间隔造成额外等待；快速点击被拒绝不续期。
- 冷却按玩家对象实例隔离，使用线程安全的弱身份键表。单人模式的客户端玩家与内置服玩家具有相同实体 ID，但各自维护预测和权威冷却；查询、写入或清理任意一端均不会覆盖另一端的截止时间。

服务端以真实放置结果为准。普通方块等 NeoForge 放置事务通过后才记冷却；桶在实际倒出成功后记冷却，拒绝发生在消费桶、支付源水经验、释放桶内生物之前。被拒的请求仍消费对应 Ctrl 输入意图，不能把本次 Ctrl 模式留给未来的另一次倒水。

客户端保留原版即时预测：若本地预测成功、之后被服务端事件取消，本地可能保留本次最多八 tick 的输入冷却；不新增自定义确认协议，也不会稍后重放被取消的放置。

普通水桶与鱼、蝌蚪、美西螈桶的临时水、Ctrl加100经验点换永久源水规则不变。水16 tick、岩浆48 tick的临时流体消退计时，与玩家八 tick 的放置冷却是两套独立机制。

## R196 实际实现

核对本地 R196 反编译源码，并用原始 class 的 `javap` 确认常量与覆盖顺序：

| 路径 | 证据 | 实际行为 |
|---|---|---|
| 首次可用 | `bdc.java:19`、`bdc.java:317` | 两个解锁时间初值为0；默认动作锁为500毫秒，覆盖锁优先，到期清理锁定。 |
| 普通放块 | `zh.java:32`、`uf.java:2396`、`uf.java:2405` | 先尝试放置，成功后客户端调用 `setUseButtonDelayOverride(250)`，即后置250毫秒；失败不创建这次覆盖锁。 |
| 普通右键 | `atv.java:1108`、`atv.java:1140`、`atv.java:1147` | 先检查是否解锁，再执行交互；成功动作随后设置默认锁，不是先等到期才执行。 |
| 桶取放 | `wr.java:15` | 不经过普通方块的250毫秒覆盖路径，成功动作采用默认500毫秒；Ctrl不改变计时。 |
| 长按与换槽 | `atv.java:1582`、`atv.java:1638`、`bdc.java:246` | 长按重复检查解锁；松键和换槽不清除现有截止时间。旧版没有副手。 |
| 服务端 | `ka.java:789` | 校验槽位、物品与射线，没有对应250/500毫秒的时间限流。 |

R196另有自动补货拾起手持物后的1500毫秒防误放限制（`bcw.java:1303`、`zh.java:54`），以及方块激活后的 `right_click_counter`（`uf.java:2267`）；它们不是普通放块的前摇。

本次采用 R196 的“先操作、成功后冷却”机制，**数值最初按用户指定统一为0.3秒，2026-10-24 调整为0.4秒，并非 R196 原值**。现代主副手共享、服务端拒绝重复请求及保留创造豁免是本项目适配，不是逐字复制旧版。

## 复测

1. 静止单击放一块，应立即出现；立即换槽或换手尝试另一块，应被拒绝，且不会稍后自行出现。
2. 冷却到期后再点，立即放下；长按正常连续搭建时相邻成功放置不少于八 tick，快速连点不把截止时间越推越后。单人内置服与独立服务器均需复测。
3. 用方块开工作台、开箱；不应先等0.4秒。碰撞失败或取消放置后，合法的下一次放置不应继承一段新冷却。
4. 普通桶、Ctrl桶和六种生物桶分别核对即时倒出、下一次限流、源水经验与单次释放；冷却中被拒不得扣费、消耗满桶或释放生物。
5. 吃蓝莓、放睡莲和粉雪，检查食用不误记放置、特殊方块不漏判。创造模式保留原行为。

自动服务端测试和不创建窗口的客户端变换审计不能替代实际客户端操作手感、网络抖动或真实多人验收。

## 2026-10-26 单人冷却失效修复

原来的 `WeakHashMap<Player, Cooldown>` 使用 `Entity.equals/hashCode`，仅按实体 ID 区分玩家。单人客户端与内置服中的玩家 ID 相同、世界对象不同；一端查询另一端写入的冷却时，世界检查会删除该记录，使预测与服务端的冷却互相清除。改用 `MapMaker.weakKeys()` 的实例身份比较，保留弱引用回收与并发访问支持。

- 新增三个集成回归：同 ID 的另一世界玩家查询、写入及清理不影响原截止时间；同一玩家修改实体 ID 后仍处于冷却。
- 旧实现运行 `mite_gameplay` 的27项GameTest，新增三项均失败，其余24项通过；日志为 `build/placement-identity-before.log`。
- 修复后 `build runGameTestServer -PmiteGameTestNamespaces=mite_gameplay -PmiteGameTestDirectory=build/verification/placement-identity-fixed-run` 成功：1763项JUnit与27项GameTest全部通过，日志为 `build/placement-identity-fixed.log`。
- 产物为 `build/libs/mite-0.2.14.jar`，已核对冷却类与当前编译输出一致，未打包GameTest类。本轮未进行真实客户端手动操作验收。
